# Ядро магазина цифровых товаров

Backend площадки цифровых товаров: каталог, заказы, приём оплаты вебхуком,
автоматическая выдача кода от внешнего поставщика, сверка и восстановление.

Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2 (async), httpx.
Очередь фоновых задач сделана на самом PostgreSQL через `FOR UPDATE SKIP LOCKED` -
брокер тут не нужен, а лишняя инфраструктура в тестовом задании только мешает.

Сделаны все пять этапов. Платёжка и два поставщика - заглушки, но заглушки
честные: отдельные процессы, своя база, реальные сетевые вызовы и реальные
таймауты. Иначе проверять этап 3 бессмысленно.

## Быстрый старт

### Docker

```bash
docker compose up --build
open http://localhost:8000/docs
```

Поднимется база, применится сид, стартуют оба поставщика и API со встроенным
воркером. Порты: API `8000`, поставщик A `9101`, поставщик B `9102`,
PostgreSQL `5433`.

### Локально

Нужен работающий PostgreSQL. Роль и две базы:

```bash
psql -d postgres -c "CREATE ROLE gamestore LOGIN PASSWORD 'gamestore' CREATEDB;"
psql -d postgres -c "CREATE DATABASE gamestore_core OWNER gamestore;"
psql -d postgres -c "CREATE DATABASE gamestore_suppliers OWNER gamestore;"
```

Дальше:

```bash
make venv     # .venv + зависимости
make seed     # схема, каталог из задания, пул из 50 ключей
make up       # поставщик A, поставщик B, API с воркером
```

Остановить - `make down`. Все настройки переопределяются переменными окружения,
список с дефолтами лежит в `.env.example`.

Проверить, что живое:

```bash
curl -s localhost:8000/health
curl -s "localhost:8000/catalog/storefront?limit=5" | python3 -m json.tool
```

## Как воспроизвести проверки

Всё ниже требует запущенного `make up`.

### Гонка: 50 параллельных вебхуков по одному заказу

```bash
make race
```

Скрипт создаёт заказ, разводит 50 корутин на барьере, отпускает их одновременно
и ждёт финального статуса:

```
created order ord_2abeb7664fae49d6 (KEY-CS2-PRIME, 1290.0 RUB)
50 webhooks in 0.80s -> {"by_result": {"ignored": 49, "applied": 1}, "by_http": {"200": 50}}
{
  "final_status": "delivered",
  "issuances": 1,
  "code": "YPLV-QK2Z-IUS5",
  "payment_events": 50,
  "applied_events": 1,
  "ledger_entries": 4
}
VERDICT: OK - ровно одна выдача
```

Обстрел одним и тем же `event_id` (критерий 2) - `make race-same-event`, там будет
`1 applied, 49 duplicate` и одна строка в журнале событий вместо пятидесяти.

Руками можно как угодно:

```bash
python -m scripts.payment_sim race --order ord_xxx --concurrency 200
python -m scripts.payment_sim pay  --order ord_которого_ещё_нет   # вебхук раньше заказа
```

### Ловушка таймаута

```bash
make trap
```

Поставщик A переводится в режим `timeout_after_issue`: он записывает выдачу кода
в свою базу и только потом зависает, так что ответ до нас не доходит. Что должно
получиться:

```
статус: delivered
выдача: RSTK-...-000 от поставщика a
попытки к поставщикам:
  a #1  unknown    req_ord_6f28...-a  timeout: ReadTimeout('')
  a #2  unknown    req_ord_6f28...-a  timeout: ReadTimeout('')
  a #3  ok         req_ord_6f28...-a  resolved by probe
уникальных request_id: 1

A: {"status":"ok","request_id":"req_ord_6f28...-a","code":"RSTK-...-000"}
B: {"detail":{"status":"not_found"}}
```

Читается так: три попытки прошли под одним `request_id`; к B мы не пошли вообще;
клиент получил ровно тот код, который A выдал в самой первой попытке.

### Отказ и фолбэк

```bash
make fallback
```

Процесс поставщика A убивается `SIGKILL`. Клиент получает connection refused -
а это точный отказ, соединение даже не установилось, значит запрос до поставщика
не дошёл и переключаться на B безопасно:

```
статус: delivered
выдача: RSTK-...-000 от поставщика b
  a #1  failed  connect: ConnectError('All connection attempts failed')
  a #2  failed  connect: ConnectError('All connection attempts failed')
  a #3  failed  connect: ConnectError('All connection attempts failed')
  b #1  ok
```

### Пустой остаток

```bash
make stock
```

```
2. статус: out_of_stock  (восстановимый, сервис жив)
3. сверка видит «оплачен, но не выдан»:
   paid_not_delivered: 1
   журнал денег сходится: True
4. пополняем остаток
5. итог (без ручного вмешательства):
   статус: delivered | код: M58F-GIIR-VJAP | попыток выдачи: 2
```

### Хаос вручную

```bash
# половина запросов 5xx, треть таймауты, из них половина "успела выдать"
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"random","error_rate":0.5,"timeout_rate":0.3,"timeout_after_issue_share":0.5}'

# детерминированные режимы: ok | error_5xx | out_of_stock | timeout |
#                           timeout_after_issue | refuse
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"timeout_after_issue","hang_seconds":5}'

# статус-запрос тоже зависает - исход становится принципиально неразрешимым
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"probe_hangs":true}'

curl -sX POST localhost:9101/a/_restock -H 'content-type: application/json' \
  -d '{"sku":"KEY-EFT","count":10}'
```

## Как это устроено

### Exactly-once живёт в схеме, а не в коде

Сервисный слой можно сломать рефакторингом, ограничение в БД - нет. Поэтому все
критичные инварианты выражены схемой:

| Ограничение | Что гарантирует |
|-------------|-----------------|
| `payment_events.event_id` PK | вебхук обрабатывается ровно один раз |
| `issuances.order_id` UNIQUE | у заказа не может быть двух выдач |
| `issuances.code` UNIQUE | один ключ не уйдёт в два заказа |
| `supplier_attempts (request_id, attempt_no)` UNIQUE | попытка фиксируется один раз |
| `ledger_entries (order_id, kind, account)` UNIQUE | проводка не задваивается |
| `jobs (kind, dedupe_key)` UNIQUE partial по `pending/running` | в очереди не висит двух одинаковых задач |

Обработчик вебхука - одна транзакция, и всё интересное происходит внутри неё:

```
INSERT INTO payment_events ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id
    ничего не вернулось -> это дубликат, выходим с 200

SELECT ... FROM orders WHERE id = :id FOR UPDATE
    параллельные вебхуки по одному заказу встают в очередь на строке

created -> paid разрешён только из created
    первый победил; остальные 49 видят статус != created и становятся no-op

INSERT INTO jobs (задача выдачи) - в этой же транзакции
```

Последняя строчка - транзакционный outbox, и она важнее, чем кажется. Между
«заказ оплачен» и «выдача запланирована» нет окна, в котором задачу можно
потерять, и нет второго хранилища, которое надо синхронизировать с базой.

Ещё одно: в обработчике вебхука нет ни одного сетевого вызова наружу. Во-первых,
контракт требует быстрый `200`. Во-вторых, держать транзакцию открытой во время
HTTP-запроса с двухсекундным таймаутом - хороший способ исчерпать пул соединений
и растянуть блокировку строки на всю длину этого таймаута. Сама выдача поэтому
разбита на три фазы: короткая транзакция (взять заказ, перевести в `delivering`),
потом сеть уже без транзакции, потом снова короткая транзакция на фиксацию.

### Таймаут - это не отказ

Тут вся суть этапа 3. Обычно исход HTTP-вызова делят надвое: получилось или нет.
Для выдачи товара этого мало, потому что «нет ответа» и «отказ» - разные вещи с
разными последствиями. Категорий три:

| Исход | Когда | Можно ли идти к следующему поставщику |
|-------|-------|--------------------------------------|
| `ok` | код получен | вопрос снят |
| `definite_failure` | connection refused, явная ошибка по этому `request_id`, `out_of_stock` | да |
| `unknown` | read timeout: запрос ушёл, ответа нет | **нет** |

Дальше всё вытекает отсюда.

`request_id` детерминированный: `req_{order_id}-{supplier}`. Не UUID - он обязан
пережить рестарт процесса и совпасть при повторе, иначе идемпотентность на стороне
поставщика бесполезна. Повтор после таймаута гарантированно возвращает тот же код.

Фолбэк разрешён только из `definite_failure`. Если A мог выдать код, а мы пойдём
в B, клиент получит два кода, а мы - двойную себестоимость. Это ровно тот случай,
когда «на всякий случай попробуем резервного» делает хуже.

`unknown` разрешается статус-запросом `GET /{s}/issue/{request_id}`. Ответ `404`
означает «такого запроса не было», исход становится `definite_failure`, и фолбэк
разрешается. Ответ `200` - забираем тот самый код. Если и статус-запрос
недоступен, заказ остаётся в восстановимом состоянии и фоновая задача повторяет
тем же `request_id` с бэкоффом. Никакого переключения. Это проверяет
`test_unresolvable_timeout_blocks_fallback`.

Отдельно различаются `ConnectError` и `ReadTimeout`. Первое значит, что соединение
не установилось и запрос физически не дошёл - точный отказ. Второе значит, что
запрос ушёл, а ответ потерялся - исход неизвестен. Разница между этими двумя
исключениями и есть разница между «безопасно переключиться» и «нельзя».

И ещё одна мелочь, которая на самом деле не мелочь: строка попытки пишется в базу
и коммитится **до** HTTP-вызова. Если процесс умрёт посреди запроса, останется
`in_flight`, и восстановление будет знать, что исход неизвестен, вместо того чтобы
решить, будто ничего и не было.

### Восстановление

Очередь на PostgreSQL: `FOR UPDATE SKIP LOCKED`, экспоненциальный бэкофф,
ограничение числа попыток. Воркеров можно поднять сколько угодно
(`docker compose --profile worker up`), задачи между ними не задваиваются.

Раз в несколько секунд «доводчик» ищет заказы, которые оплачены, но не
финализированы дольше `STUCK_ORDER_SECONDS`, и ставит им ту же самую задачу
выдачи. Делать так безопасно ровно потому, что задача идемпотентна на всех
уровнях сразу: дедупликация в очереди, блокировка строки заказа, `UNIQUE(order_id)`
на выдаче и разрешение неизвестных исходов перед каждым повтором.

Вебхук, пришедший раньше заказа, сохраняется со статусом `orphan` и получает
`200`. Отвечать `5xx` тут неправильно - платёжка начнёт ретраить то, что мы уже
успешно сохранили. Когда заказ появляется, накопленные события применяются в
порядке `event_created_at`.

Статусы `out_of_stock` и `delivery_failed` не терминальные. После пополнения
остатка или выздоровления поставщика заказ доходит до `delivered` сам, без
ручного вмешательства.

### Деньги

Двойная запись: `amount_minor > 0` это дебет, `< 0` кредит, сумма строк одной
проводки равна нулю. Отсюда и «журнал, который всегда сходится»: раз каждая
проводка нулевая, нулевой будет и весь журнал. Проверяется в
`/admin/ledger/balance` и в тестах.

| Событие | Проводка |
|---------|----------|
| Оплата принята | `customer` +сумма, `revenue` -сумма |
| Код выдан | `supplier_cost` +себестоимость, `inventory` -себестоимость |
| Возврат | `refund` +сумма, `customer` -сумма |

Суммы хранятся целыми в копейках. Float на деньгах не бывает.

### Логи

Структурированный JSON, сквозные поля `order_id`, `event_id`, `request_id`,
`supplier`. История одного заказа собирается грепом:

```bash
grep '"order_id": "ord_xxx"' logs | jq -c '{ts: .timestamp, event, status, reason}'
```

Основные события: `order.created`, `payment.captured`, `payment.duplicate`,
`payment.noop`, `payment.orphan`, `payment.out_of_order`, `payment.amount_mismatch`,
`delivery.started`, `delivery.completed`, `delivery.out_of_stock`,
`supplier.timeout`, `supplier.probe`, `supplier.unresolved`, `supplier.failover`,
`supplier.recovered_code`, `sweeper.requeued_stuck_order`.

То же самое, но структурированно и по одному заказу, отдаёт
`/admin/orders/{id}/timeline`.

## Каталог под нагрузкой

```bash
make catalog    # сгенерировать 50 000 SKU и замерить
make explain    # только план и замеры на текущем каталоге
```

На 50 012 SKU (`products` 25 MB, `sku_stock` 8 MB):

```
Горячий запрос (300 прогонов, LIMIT 50): p50=0.18ms  p95=0.37ms  max=0.56ms
То же с OFFSET (антипаттерн):            p50=19.27ms p95=31.06ms max=34.34ms
```

План:

```
Limit  (actual time=0.058..0.274 rows=50)
  ->  Nested Loop  (actual rows=50)
        ->  Index Only Scan using ix_products_storefront_by_type on products
              Index Cond: ((type = 'key') AND (sku > 'LOAD-0010000'))
              Heap Fetches: 0        Buffers: shared hit=6      actual rows=59
        ->  Index Only Scan using ix_sku_stock_covering on sku_stock  (loops=59)
              Index Cond: (sku = p.sku)
              Heap Fetches: 0
Execution Time: 0.308 ms
```

Что за этим стоит.

**Остаток вынесен из карточки товара.** `products` широкая и почти статичная,
`sku_stock` узкая и горячая. Если держать счётчик прямо в `products`, каждая
выдача переписывает широкую строку и обновляет все её индексы. Плюс `fillfactor
= 80` на `sku_stock`, чтобы апдейты счётчика шли по HOT-пути.

**Покрывающие частичные индексы.** Всё, что рисуется в карточке витрины, лежит
в `INCLUDE`, так что скан идёт `Index Only`, `Heap Fetches` ноль:

```sql
CREATE INDEX ix_products_storefront_by_type ON products (type, sku)
    INCLUDE (name, price_minor, currency, image) WHERE is_active;
```

Здесь есть тонкость, на которой я потерял больше всего времени. Предикат надо
писать `WHERE is_active`, а не `WHERE is_active IS TRUE`. Доказыватель предикатов
PostgreSQL сопоставляет формы буквально, и во втором варианте частичный индекс
просто перестаёт применяться - молча, без единого предупреждения. Планировщик
уходит на PK со скрытым фильтром, и получается 6.5 мс вместо 0.3. Проверяется
тестом `test_covering_index_is_usable_by_the_planner`, чтобы это не вернулось.

**Keyset вместо OFFSET.** OFFSET на глубокой странице читает и выбрасывает всё,
что перед ней:

| OFFSET | p50 |
|--------|-----|
| 0 | 0.44 ms |
| 1 000 | 3.97 ms |
| 5 000 | 18.13 ms |
| 10 000 | 35.76 ms |

Keyset (`WHERE sku > :cursor`) всегда читает ровно `limit` строк - 0.18 мс на
любой странице.

**`JOIN LATERAL (... LIMIT 1)` вместо обычного join.** Без `LIMIT 1` PostgreSQL
разворачивает подзапрос и на недооценке селективности уходит в merge join,
который прочитывает всю таблицу остатков: 2 мс, и растёт вместе с каталогом.
`LIMIT 1` мешает разворачиванию и фиксирует план: индексный проход по товарам,
затем ровно `limit` точечных обращений по PK. Стоимость перестаёт зависеть от
размера каталога.

**`VACUUM (ANALYZE)` после массовой загрузки.** Пока visibility map не обновлена,
`Index Only Scan` всё равно ходит в кучу, и от покрывающего индекса нет никакого
толку. Это делают и `scripts/load_catalog.py`, и `scripts/seed.py`. Тоже из
разряда «полдня искал, одна строчка».

**`ORDER BY type, sku` при фильтре по типу.** При фиксированном `type` это то же
самое, что `ORDER BY sku`, но совпадает с порядком ключа составного индекса, и
планировщик уверенно берёт покрывающий индекс вместо PK.

**Лишних индексов нет.** Отдельный индекс по `available` напрашивается, но его
здесь нет: витрина ходит в остатки только точечно по `sku`, а каждый лишний
индекс - это лишняя запись на каждой выдаче.

## Куда расти дальше

**Чтение.** Витрина уже не зависит от размера каталога. Дальше - реплики на
чтение и кеш страниц (ключ это фильтр плюс курсор, TTL десятки секунд, сброс
по событию изменения остатка).

**Запись.** Узкое место не выдача, а `sku_stock` при массовых продажах одного
SKU: все транзакции дерутся за одну строку. Лечится батчингом апдейтов или
«монетницей» - несколько строк-счётчиков на SKU с суммированием при чтении.

**Очередь.** `SKIP LOCKED` масштабируется добавлением воркеров линейно. Когда
таблица `jobs` станет горячей - партиционирование по `kind` и вынос завершённых
задач в архив. Отдельный брокер понадобится не раньше, чем у этих событий
появится второй потребитель.

**Заказы и события.** `orders` и `payment_events` растут монотонно, значит
партиционирование по месяцам и старые партиции в холодное хранилище. Шардирование
по `order_id` возможно без переделки логики: все критичные транзакции локальны
для одного заказа, распределённых блокировок нет.

**Поставщики.** Пул расширяется списком в `SUPPLIER_ORDER`, логика трёх исходов
от их количества не зависит. Чего сейчас не хватает - circuit breaker на
поставщика (ретраи с бэкоффом есть, размыкателя нет) и общего бюджета повторов
на заказ, чтобы один мёртвый поставщик не съедал воркеры.

## Время и рамки

Примерно **6 часов** от разбора задания до готового репозитория с тестами и
документацией. Больше всего съели два места: этап 3 (пока не разложил исходы на
три категории вместо двух, всё получалось либо небезопасно, либо слишком
консервативно) и этап 5 (довести план до `Index Only Scan` оказалось не так
просто, см. историю с предикатом индекса и visibility map).

Чего сознательно не делал:

- подпись вебхука не проверяется - в задании это явно исключено;
- схема создаётся идемпотентным DDL, а не Alembic;
- на `/admin/*` нет авторизации - это внутренние, в проде они за отдельным
  контуром;
- фронтенда нет, реального эквайринга и реальных поставщиков тоже, как указано в задании.
