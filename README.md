# Ядро магазина цифровых товаров

Backend площадки цифровых товаров: каталог, многотоварные заказы, приём оплаты
вебхуком, автоматическая выдача кодов от внешних поставщиков, возвраты, сверка,
восстановление и история, по которой видно состояние на любой прошлый момент.

Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2 (async), httpx.
Очередь фоновых задач сделана на самом PostgreSQL через `FOR UPDATE SKIP LOCKED` -
брокер тут не нужен, а лишняя инфраструктура в тестовом задании только мешает.

Платёжка и два поставщика - заглушки, но честные: отдельные процессы, своя база,
реальные сетевые вызовы и реальные таймауты. На моках проверять тут нечего.

Что решено во втором этапе:

| Задача | Ответ |
|--------|-------|
| Заказ из нескольких товаров, часть не выдаётся | единица выдачи - позиция, выданное остаётся у покупателя, за невыданное деньги возвращаются автоматически |
| Деньги сходятся при любом сбое и повторе | инвариант `оплачено = выдано + возвращено` держится схемой счетов, а не проверками |
| Поставщику нельзя доверять | код проверяется по владельцу, ошибка не принимается на веру, повтор идёт под новым поколением `request_id` |
| Всплеск заказов и лимит поставщика | token bucket в БД, очередь с приоритетом оплаченных, прогресс наружу |
| Картина на любой прошлый момент | append-only история с запретом на UPDATE и DELETE в самой БД |

## Быстрый старт

### Docker

```bash
docker compose up --build
open http://localhost:8000/docs
```

Поднимется база, применится сид, стартуют оба поставщика и API со встроенным
воркером. Порты: API `8000`, поставщик A `9101`, поставщик B `9102`,
PostgreSQL `5433`.

### Локально

Нужен работающий PostgreSQL. Роль и две базы:

```bash
psql -d postgres -c "CREATE ROLE gamestore LOGIN PASSWORD 'gamestore' CREATEDB;"
psql -d postgres -c "CREATE DATABASE gamestore_core OWNER gamestore;"
psql -d postgres -c "CREATE DATABASE gamestore_suppliers OWNER gamestore;"
```

Дальше:

```bash
make venv     # .venv + зависимости
make seed     # схема, каталог из задания, пул из 50 ключей
make up       # поставщик A, поставщик B, API с воркером
```

Остановить - `make down`. Все настройки переопределяются переменными окружения,
список с дефолтами лежит в `.env.example`.

Проверить, что живое:

```bash
curl -s localhost:8000/health
curl -s "localhost:8000/catalog/storefront?limit=5" | python3 -m json.tool
```

```bash
make test              # всё, 65 тестов, около 70 секунд
make test-partial      # частичный сбой заказа и сходимость денег

make test-history      # состояние на прошлый момент и итоги за период
make test-race         # гонки и идемпотентность
make test-suppliers    # таймауты и фолбэк
```

Тесты поднимают собственный стек на портах `8123/9123/9124` и отдельные базы
`*_test`, так что запущенному `make up` они не мешают.

Гоняются они через живой HTTP и живой PostgreSQL, а не через ASGI-транспорт.
Это дольше, но по-другому нельзя: ни гонка на `SELECT FOR UPDATE`, ни read
timeout к поставщику на моках не воспроизводятся, а проверять надо именно их.

## Как воспроизвести проверки

Всё ниже требует запущенного `make up`.

### Гонка: 50 параллельных вебхуков по одному заказу

```bash
make race
```

Скрипт создаёт заказ, разводит 50 корутин на барьере, отпускает их одновременно
и ждёт финального статуса:

```
created order ord_2abeb7664fae49d6 (KEY-CS2-PRIME, 1290.0 RUB)
50 webhooks in 0.80s -> {"by_result": {"ignored": 49, "applied": 1}, "by_http": {"200": 50}}
{
  "final_status": "delivered",
  "issuances": 1,
  "code": "YPLV-QK2Z-IUS5",
  "payment_events": 50,
  "applied_events": 1,
  "ledger_entries": 4
}
VERDICT: OK - ровно одна выдача
```

Обстрел одним и тем же `event_id` (критерий 2) - `make race-same-event`, там будет
`1 applied, 49 duplicate` и одна строка в журнале событий вместо пятидесяти.

Руками можно как угодно:

```bash
python -m scripts.payment_sim race --order ord_xxx --concurrency 200
python -m scripts.payment_sim pay  --order ord_которого_ещё_нет   # вебхук раньше заказа
```

### Ловушка таймаута

```bash
make trap
```

Поставщик A переводится в режим `timeout_after_issue`: он записывает выдачу кода
в свою базу и только потом зависает, так что ответ до нас не доходит. Что должно
получиться:

```
статус: delivered
выдача: RSTK-...-000 от поставщика a
попытки к поставщикам:
  a #1  unknown    req_ord_6f28...-a  timeout: ReadTimeout('')
  a #2  unknown    req_ord_6f28...-a  timeout: ReadTimeout('')
  a #3  ok         req_ord_6f28...-a  resolved by probe
уникальных request_id: 1

A: {"status":"ok","request_id":"req_ord_6f28...-a","code":"RSTK-...-000"}
B: {"detail":{"status":"not_found"}}
```

Читается так: три попытки прошли под одним `request_id`; к B мы не пошли вообще;
клиент получил ровно тот код, который A выдал в самой первой попытке.

### Отказ и фолбэк

```bash
make fallback
```

Процесс поставщика A убивается `SIGKILL`. Клиент получает connection refused -
а это точный отказ, соединение даже не установилось, значит запрос до поставщика
не дошёл и переключаться на B безопасно:

```
статус: delivered
выдача: RSTK-...-000 от поставщика b
  a #1  failed  connect: ConnectError('All connection attempts failed')
  a #2  failed  connect: ConnectError('All connection attempts failed')
  a #3  failed  connect: ConnectError('All connection attempts failed')
  b #1  ok
```

### Пустой остаток

```bash
make stock
```

```
2. статус: out_of_stock  (восстановимый, сервис жив)
3. сверка видит «оплачен, но не выдан»:
   paid_not_delivered: 1
   журнал денег сходится: True
4. пополняем остаток
5. итог (без ручного вмешательства):
   статус: delivered | код: M58F-GIIR-VJAP | попыток выдачи: 2
```

### Частичный сбой заказа

Один товар в заказе не выдаётся, остальные выдаются. Поставщики отвечают на
`KEY-EFT` кодом 410 `sku_not_supported` - это отказ навсегда, в отличие от
`out_of_stock`, поэтому ждать нечего и за позицию возвращаются деньги.

```bash
for p in 9101:a 9102:b; do
  curl -sX POST localhost:${p%:*}/${p#*:}/_control -H 'content-type: application/json' \
    -d '{"unsupported_skus":["KEY-EFT"]}'
done

ORDER=$(curl -sX POST localhost:8000/orders -H 'content-type: application/json' \
  -d '{"items":[{"sku":"KEY-CS2-PRIME"},{"sku":"KEY-EFT"},{"sku":"GIFT-PSN-1000"}]}' | jq -r .id)
python -m scripts.payment_sim pay --order $ORDER

sleep 3
curl -s localhost:8000/orders/$ORDER | jq '{status, items: [.items[] | {sku, status, code: .issuance.code}]}'
```

```json
{
  "status": "partially_delivered",
  "items": [
    { "sku": "KEY-CS2-PRIME",  "status": "delivered", "code": "EXTA-KEY-CS2-PRIME-00000" },
    { "sku": "KEY-EFT",        "status": "refunded",  "code": null },
    { "sku": "GIFT-PSN-1000",  "status": "delivered", "code": "EXTA-GIFT-PSN-1000-00000" }
  ]
}
```

Деньги по этому заказу:

```bash
curl -s localhost:8000/admin/money | jq
# "equation": "578000 = 229000 + 349000 + 0",  "balanced": true
```

Выдано 1290 + 1000 рублей, возвращено 3490, оплачено 5780. Сходится.
Возврат не разовый: повторить шаг выдачи (`/admin/orders/{id}/redeliver`) или
возврат (`/admin/orders/{id}/refund`) можно сколько угодно - вторых выдач и
вторых проводок не появится.

### Недобросовестный поставщик

Три режима, ответу ни в одном верить нельзя.

```bash
# 1. отдаёт код, уже выданный другому заказу
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"duplicate_code"}'

# 2. отдаёт код от другого товара
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"foreign_code"}'

# 3. записывает выдачу у себя и отвечает 500
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"error_after_issue"}'
```

Заказ на `STEAM-TOPUP-1000` при включённом `duplicate_code` (второй заказ на тот
же SKU, код первого уже выдан):

```bash
curl -s localhost:8000/admin/orders/$ORDER/timeline \
  | jq '{attempts: [.supplier_attempts[] | {supplier, code, state}],
         discrepancies: .supplier_discrepancies, issuances: .issuances}'
```

```json
{
  "attempts": [
    { "supplier": "a", "code": "EXTA-STEAM-TOPUP-1000-00000", "state": "ok" },
    { "supplier": "b", "code": "P3EI-W8UO-9B4K",              "state": "ok" }
  ],
  "discrepancies": [
    { "supplier": "a", "kind": "duplicate_code",
      "code": "EXTA-STEAM-TOPUP-1000-00000",
      "detail": "code belongs to req_ord_3df5e7ec011745da.1-a",
      "resolved_at": "...", "resolution": "reissued" }
  ],
  "issuances": [
    { "code": "P3EI-W8UO-9B4K", "supplier": "b" }
  ]
}
```

Читается так: A вернул код, который уже принадлежит другому запросу; мы это
увидели по `GET /a/codes/{code}`, клиенту его не отдали, зафиксировали
расхождение и взяли код у B. Владелец первого кода не пострадал.

`error_after_issue` разбирается иначе: перед уходом к B мы спрашиваем у A статус
по `request_id`, находим там код и отдаём именно его. В таймлайне появится
расхождение `phantom_error` с `resolution: "code recovered by status probe"`, а
выдача останется одна и от A.

Сводка по всем расхождениям:

```bash
curl -s localhost:8000/admin/discrepancies | jq
# by_kind: [{"kind":"duplicate_code","total":1,"open":0}]
# needs_attention: {"count":0}   <- разобранных руками не потребовалось
```

### Всплеск заказов и лимит поставщика

Ставим поставщикам лимит 20 запросов в секунду и оплачиваем 24 заказа разом:

```bash
for p in 9101:a 9102:b; do
  curl -sX POST localhost:${p%:*}/${p#*:}/_stats/reset
  curl -sX POST localhost:${p%:*}/${p#*:}/_control -H 'content-type: application/json' \
    -d '{"rate_limit":20,"rate_window_seconds":1.0}'
done
# ... 24 заказа с оплатой ...
curl -s localhost:8000/admin/queue | jq
```

Во время всплеска видно очередь и бюджеты:

```json
{
  "queue":  { "waiting": 17, "by_kind": [
      { "kind": "deliver_order", "state": "running", "priority": 0, "n": 17,
        "oldest_seconds": 0.1 } ] },
  "paid_items": { "total": 29, "delivered": 11, "refunded": 1, "in_progress": 17 },
  "suppliers": [
    { "supplier": "a", "tokens_available": 1.0, "capacity": 1.0,
      "rate_per_min": 540.0, "taken_total": 13, "throttled_total": 105 }
  ]
}
```

Через несколько секунд `waiting: 0`, `in_progress: 0`, все заказы выданы. Что
при этом видел сам поставщик:

```bash
curl -s localhost:9101/a/_stats | jq
```

```json
{ "rate_limit": 20, "rate_window_seconds": 1.0,
  "accepted": 24, "rejected_429": 0, "over_limit": 0, "max_in_window": 5 }
```

`over_limit: 0` и `rejected_429: 0` - лимит не просто не превышен, мы к нему
даже не подошли вплотную. Это счётчик заглушки, а не наше самоощущение.

### Хаос вручную

```bash
# половина запросов 5xx, треть таймауты, из них половина "успела выдать"
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"random","error_rate":0.5,"timeout_rate":0.3,"timeout_after_issue_share":0.5}'

# детерминированные режимы: ok | error_5xx | out_of_stock | timeout |
#   timeout_after_issue | refuse | duplicate_code | foreign_code | error_after_issue
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"mode":"timeout_after_issue","hang_seconds":5}'

# статус-запрос тоже зависает - исход становится принципиально неразрешимым
curl -sX POST localhost:9101/a/_control -H 'content-type: application/json' \
  -d '{"probe_hangs":true}'

curl -sX POST localhost:9101/a/_restock -H 'content-type: application/json' \
  -d '{"sku":"KEY-EFT","count":10}'
```

## Как проверить, что деньги сходятся

Три способа, от самого короткого к самому дотошному.

**Одна ручка.** Инвариант задания целиком:

```bash
make money      # или curl -s localhost:8000/admin/money | jq
```

```json
{ "paid_minor": 1978000, "delivered_minor": 1629000, "refunded_minor": 349000,
  "open_minor": 0, "equation": "1978000 = 1629000 + 349000 + 0",
  "balanced": true, "unsettled_finished_orders": { "count": 0, "items": [] } }
```

`open_minor` - деньги, за которые мы ещё не отчитались ни кодом, ни возвратом
(заказы в работе). `unsettled_finished_orders` - завершённые заказы, у которых
обязательство перед клиентом не закрылось в ноль; в норме там пусто, а любая
строка означает реальную дыру.

**Сверка целиком.** Та же проверка плюс расхождения в обе стороны:

```bash
make reconcile
```

```json
{ "paid_not_delivered": { "count": 0 }, "delivered_not_paid": { "count": 0 },
  "ledger":  { "balanced": true, "total_minor": 0 },
  "money":   { "balanced": true, "equation": "1978000 = 1629000 + 349000 + 0" },
  "supplier_discrepancies": { "needs_attention": { "count": 0 } },
  "healthy": true }
```

`healthy` - короткий вердикт для мониторинга: нет расхождений товара, журнал
сходится в ноль, денежное уравнение выполняется, неразобранных расхождений с
поставщиками нет.

**По конкретному заказу.** В таймлайне видно каждую проводку:

```bash
curl -s localhost:8000/admin/orders/$ORDER/timeline \
  | jq '[.ledger_entries[] | {kind, item_id, account, amount_minor}]'
```

Сумма по всем строкам заказа равна нулю, сумма по счёту `customer` тоже - это и
означает, что за каждую копейку отчитались кодом или возвратом.

Отдельно проверяется, что уравнение держится **на любой момент в прошлом**, а не
только сейчас:

```bash
curl -s "localhost:8000/admin/money/as-of?at=2026-09-08T10:22:36Z" | jq .equation
curl -s "localhost:8000/admin/reports/period?from=...&to=..." | jq .money
```

Итог за период считается из журналов и совпадает с разностью двух срезов.
В тестах это `test_money_equation_holds_globally` и `test_period_totals_add_up`.

## Как это устроено

### Exactly-once живёт в схеме, а не в коде

Сервисный слой можно сломать рефакторингом, ограничение в БД - нет. Поэтому все
критичные инварианты выражены схемой:

| Ограничение | Что гарантирует |
|-------------|-----------------|
| `payment_events.event_id` PK | вебхук обрабатывается ровно один раз |
| `issuances.order_item_id` UNIQUE | у позиции не может быть двух выдач |
| `issuances.code` UNIQUE | один ключ не уйдёт в два заказа |
| `order_items (order_id, position)` UNIQUE | позиция заказа не задваивается |
| `supplier_attempts (request_id, attempt_no)` UNIQUE | попытка фиксируется один раз |
| `ledger_entries (order_id, item_id, kind, account)` UNIQUE | проводка не задваивается |
| `jobs (kind, dedupe_key)` UNIQUE partial по `pending/running` | в очереди не висит двух одинаковых задач |
| триггер на `order_events` и `ledger_entries` | историю нельзя переписать задним числом |

Обработчик вебхука - одна транзакция, и всё интересное происходит внутри неё:

```
INSERT INTO payment_events ... ON CONFLICT (event_id) DO NOTHING RETURNING event_id
    ничего не вернулось -> это дубликат, выходим с 200

SELECT ... FROM orders WHERE id = :id FOR UPDATE
    параллельные вебхуки по одному заказу встают в очередь на строке

created -> paid разрешён только из created
    первый победил; остальные 49 видят статус != created и становятся no-op

INSERT INTO jobs (задача выдачи) - в этой же транзакции
```

Последняя строчка - транзакционный outbox, и она важнее, чем кажется. Между
«заказ оплачен» и «выдача запланирована» нет окна, в котором задачу можно
потерять, и нет второго хранилища, которое надо синхронизировать с базой.

Ещё одно: в обработчике вебхука нет ни одного сетевого вызова наружу. Во-первых,
контракт требует быстрый `200`. Во-вторых, держать транзакцию открытой во время
HTTP-запроса с двухсекундным таймаутом - хороший способ исчерпать пул соединений
и растянуть блокировку строки на всю длину этого таймаута. Сама выдача поэтому
разбита на три фазы: короткая транзакция (взять заказ, перевести в `delivering`),
потом сеть уже без транзакции, потом снова короткая транзакция на фиксацию.

### Таймаут - это не отказ

Обычно исход HTTP-вызова делят надвое: получилось или нет.
Для выдачи товара этого мало, потому что «нет ответа» и «отказ» - разные вещи с
разными последствиями. Категорий три:

| Исход | Когда | Можно ли идти к следующему поставщику |
|-------|-------|--------------------------------------|
| `ok` | код получен | вопрос снят |
| `definite_failure` | connection refused, явная ошибка по этому `request_id`, `out_of_stock` | да |
| `unknown` | read timeout: запрос ушёл, ответа нет | **нет** |

Дальше всё вытекает отсюда.

`request_id` детерминированный: `req_{item_id}-{supplier}`. Не UUID - он обязан
пережить рестарт процесса и совпасть при повторе, иначе идемпотентность на стороне
поставщика бесполезна. Повтор после таймаута гарантированно возвращает тот же код.

Фолбэк разрешён только из `definite_failure`. Если A мог выдать код, а мы пойдём
в B, клиент получит два кода, а мы - двойную себестоимость. Это ровно тот случай,
когда «на всякий случай попробуем резервного» делает хуже.

`unknown` разрешается статус-запросом `GET /{s}/issue/{request_id}`. Ответ `404`
означает «такого запроса не было», исход становится `definite_failure`, и фолбэк
разрешается. Ответ `200` - забираем тот самый код. Если и статус-запрос
недоступен, заказ остаётся в восстановимом состоянии и фоновая задача повторяет
тем же `request_id` с бэкоффом. Никакого переключения. Это проверяет
`test_unresolvable_timeout_blocks_fallback`.

Отдельно различаются `ConnectError` и `ReadTimeout`. Первое значит, что соединение
не установилось и запрос физически не дошёл - точный отказ. Второе значит, что
запрос ушёл, а ответ потерялся - исход неизвестен. Разница между этими двумя
исключениями и есть разница между «безопасно переключиться» и «нельзя».

И ещё одна мелочь, которая на самом деле не мелочь: строка попытки пишется в базу
и коммитится **до** HTTP-вызова. Если процесс умрёт посреди запроса, останется
`in_flight`, и восстановление будет знать, что исход неизвестен, вместо того чтобы
решить, будто ничего и не было.

### Восстановление

Очередь на PostgreSQL: `FOR UPDATE SKIP LOCKED`, экспоненциальный бэкофф,
ограничение числа попыток. Воркеров можно поднять сколько угодно
(`docker compose --profile worker up`), задачи между ними не задваиваются.

Раз в несколько секунд «доводчик» ищет заказы, которые оплачены, но не
финализированы дольше `STUCK_ORDER_SECONDS`, и ставит им ту же самую задачу
выдачи. Делать так безопасно ровно потому, что задача идемпотентна на всех
уровнях сразу: дедупликация в очереди, блокировка строки позиции,
`UNIQUE(order_item_id)` на выдаче и разрешение неизвестных исходов перед каждым
повтором.

Вебхук, пришедший раньше заказа, сохраняется со статусом `orphan` и получает
`200`. Отвечать `5xx` тут неправильно - платёжка начнёт ретраить то, что мы уже
успешно сохранили. Когда заказ появляется, накопленные события применяются в
порядке `event_created_at`.

Статусы `out_of_stock` и `delivery_failed` не терминальные. После пополнения
остатка или выздоровления поставщика заказ доходит до `delivered` сам, без
ручного вмешательства.

### Деньги

Двойная запись: `amount_minor > 0` это дебет, `< 0` кредит, сумма строк одной
проводки равна нулю. Отсюда «журнал, который всегда сходится»: раз каждая
проводка нулевая, нулевой будет и весь журнал.

Инвариант задания «оплачено = выдано + возвращено» - не отдельная проверка, а
следствие схемы счетов. Оплата ставит обязательство на `customer`, выдача и
возврат его гасят:

| Событие | Уровень | Проводка |
|---------|---------|----------|
| Оплата принята | заказ | `customer` +сумма, `revenue` -сумма |
| Код выдан | позиция | `delivered` +сумма, `customer` -сумма |
| Себестоимость выдачи | позиция | `supplier_cost` +с/с, `inventory` -с/с |
| Возврат за позицию | позиция | `refund` +сумма, `customer` -сумма |

Значит, у завершённого заказа остаток по `customer` обязан быть нулём, а у
незавершённого равен сумме, за которую мы ещё не отчитались ни кодом, ни
деньгами. Проверка сводится к одному `SELECT`, а не к сверке трёх таблиц, и
работает не только «сейчас», но и на любом прошлом срезе.

Задвоить проводку не даёт `UNIQUE(order_id, item_id, kind, account)` - это
важно, потому что все обработчики идемпотентны и повторяются штатно.

Суммы хранятся целыми в копейках. Float на деньгах не бывает.

### Позиция закрывается ровно одним способом

Единица выдачи, денег и идемпотентности - позиция заказа, а не заказ. Каждая
закрывается кодом либо деньгами, и оба пути защищены схемой:

| Способ | Что не даёт задвоить |
|--------|----------------------|
| выдача | `issuances.order_item_id` UNIQUE |
| возврат | `order_items.status='refunded'` плюс UNIQUE проводки |

Отсюда и берётся сходимость: каждая позиция оплаченного заказа рано или поздно
попадает ровно в одно слагаемое. Заказ - агрегат: `delivered`, если выданы все
позиции, `partially_delivered`, если часть закрыта деньгами, `refunded`, если
не выдано ничего.

Решение «вернуть деньги» принимается по двум признакам: позиция `unavailable`
(поставщики такое не продают, ждать нечего) или исчерпан бюджет попыток.
`out_of_stock` сам по себе поводом не является - остаток завозят, и заказ
доводится сам. Если бюджет фоновой задачи всё-таки кончился, воркер не бросает
заказ в подвешенном состоянии, а закрывает невыданное возвратом.

### Поставщику нельзя доверять

Первый этап исходил из того, что поставщик честен и врать может только сеть.
Второй снимает и это допущение: поставщик может отдать чужой код, код от
другого товара или ответить ошибкой, выдав код на самом деле.

| Что делает поставщик | Что делаем мы |
|----------------------|---------------|
| отдал уже выданный код | сверяем владельца через `GET /{s}/codes/{code}`, отвергаем, берём другой |
| отдал код от другого SKU | та же сверка, `kind = foreign_code` |
| ответил ошибкой, выдав код | перед фолбэком спрашиваем статус по `request_id` и забираем найденный код |
| прислал код, о котором сам не знает | `kind = unknown_code`, клиенту не уходит |
| код уже принадлежит другой позиции | ловит `issuances.code` UNIQUE, `kind = code_collision` |

Отвергнутый код нельзя переспросить тем же `request_id`: по идемпотентности
поставщик вернёт тот же мусор. Поэтому повтор идёт под следующим **поколением**
`request_id` (`req_ord_xxx.1-a`, затем `req_ord_xxx.1-a-g2`), а номер поколения
считается как число зафиксированных расхождений по паре (позиция, поставщик) -
то есть переживает рестарт и не требует отдельного счётчика.

Расхождения складываются в `supplier_discrepancies` и закрываются сами, когда
позиция закрыта кодом или деньгами. `/admin/discrepancies` показывает сводку и
отдельно `needs_attention` - открытые расхождения по уже закрытым позициям,
то есть то, чего быть не должно.

### Лимит поставщика и очередь

Лимит держится на своей стороне, а не разбирается по 429: ответ 429 приходит
уже после того, как лимит превышен. Token bucket живёт в таблице
`supplier_budgets`, а не в памяти процесса - лимит принадлежит поставщику, и два
воркера с локальными счётчиками превысили бы его вдвое. Токен снимается одним
атомарным `UPDATE`, блокировка строки и есть сериализация.

Bucket намеренно узкий (`SUPPLIER_RATE_BURST`, по умолчанию 1): окно у
поставщика скользящее, и полный bucket в его начале даёт всплеск, который в это
окно не помещается. Плюс запас `SUPPLIER_RATE_SAFETY` на расхождение часов.

Если токена нет, задача возвращается в очередь **не тратя попытку**
(`attempts` откатывается) - иначе всплеск нагрузки закончился бы возвратами
денег вместо выдач. Счётчик попыток позиции откатывается по той же причине:
ожидание своего окна не является неудачной выдачей.

Очередь разбирается в порядке `priority, run_at`. Выдача оплаченного заказа - 0,
возврат - 10, досылка «сиротских» платежей - 20, синхронизация витрины - 50. При
этом самая сильная форма требования «оплаченные раньше неоплаченных» выполняется
и без приоритетов: к поставщику по неоплаченному заказу не ходят вовсе.

### История, по которой видно прошлое

`orders` и `order_items` отвечают на вопрос «как сейчас» - их переписывает каждый
шаг выдачи. На вопрос «как было в 14:32» отвечают два append-only журнала:
события заказа и проводки.

Событие пишется **той же транзакцией**, что и само изменение. Отдельной
транзакцией появилось бы окно, в котором состояние уже другое, а история об этом
ещё не знает. И пишется только если изменение действительно применилось: выдача,
начатая до возврата, не должна дописывать в историю статус, которого в таблице
нет.

Запрет на переписывание - не соглашение внутри кода, а триггер в БД:

```sql
UPDATE order_events SET order_id = 'hacked';
-- ERROR: append-only table order_events: UPDATE is not allowed
```

Состояние на момент `T` - свёртка событий до `T`, деньги - сумма проводок до
`T`. Итог за период считается из тех же журналов и совпадает с разностью двух
срезов: одно и то же число, полученное двумя независимыми способами.

### Логи

Структурированный JSON, сквозные поля `order_id`, `event_id`, `request_id`,
`supplier`. История одного заказа собирается грепом:

```bash
grep '"order_id": "ord_xxx"' logs | jq -c '{ts: .timestamp, event, status, reason}'
```

Основные события: `order.created`, `payment.captured`, `payment.duplicate`,
`payment.noop`, `payment.orphan`, `payment.out_of_order`, `payment.amount_mismatch`,
`delivery.started`, `delivery.completed`, `delivery.out_of_stock`,
`supplier.timeout`, `supplier.probe`, `supplier.unresolved`, `supplier.failover`,
`supplier.recovered_code`, `sweeper.requeued_stuck_order`.

То же самое, но структурированно и по одному заказу, отдаёт
`/admin/orders/{id}/timeline`.

## Каталог под нагрузкой

```bash
make catalog    # сгенерировать 50 000 SKU и замерить
make explain    # только план и замеры на текущем каталоге
```

На 50 012 SKU (`products` 25 MB, `sku_stock` 8 MB):

```
Горячий запрос (300 прогонов, LIMIT 50): p50=0.18ms  p95=0.37ms  max=0.56ms
То же с OFFSET (антипаттерн):            p50=19.27ms p95=31.06ms max=34.34ms
```

План:

```
Limit  (actual time=0.058..0.274 rows=50)
  ->  Nested Loop  (actual rows=50)
        ->  Index Only Scan using ix_products_storefront_by_type on products
              Index Cond: ((type = 'key') AND (sku > 'LOAD-0010000'))
              Heap Fetches: 0        Buffers: shared hit=6      actual rows=59
        ->  Index Only Scan using ix_sku_stock_covering on sku_stock  (loops=59)
              Index Cond: (sku = p.sku)
              Heap Fetches: 0
Execution Time: 0.308 ms
```

Что за этим стоит.

**Остаток вынесен из карточки товара.** `products` широкая и почти статичная,
`sku_stock` узкая и горячая. Если держать счётчик прямо в `products`, каждая
выдача переписывает широкую строку и обновляет все её индексы. Плюс `fillfactor
= 80` на `sku_stock`, чтобы апдейты счётчика шли по HOT-пути.

**Покрывающие частичные индексы.** Всё, что рисуется в карточке витрины, лежит
в `INCLUDE`, так что скан идёт `Index Only`, `Heap Fetches` ноль:

```sql
CREATE INDEX ix_products_storefront_by_type ON products (type, sku)
    INCLUDE (name, price_minor, currency, image) WHERE is_active;
```

Здесь есть тонкость, на которой я потерял больше всего времени. Предикат надо
писать `WHERE is_active`, а не `WHERE is_active IS TRUE`. Доказыватель предикатов
PostgreSQL сопоставляет формы буквально, и во втором варианте частичный индекс
просто перестаёт применяться - молча, без единого предупреждения. Планировщик
уходит на PK со скрытым фильтром, и получается 6.5 мс вместо 0.3. Проверяется
тестом `test_covering_index_is_usable_by_the_planner`, чтобы это не вернулось.

**Keyset вместо OFFSET.** OFFSET на глубокой странице читает и выбрасывает всё,
что перед ней:

| OFFSET | p50 |
|--------|-----|
| 0 | 0.44 ms |
| 1 000 | 3.97 ms |
| 5 000 | 18.13 ms |
| 10 000 | 35.76 ms |

Keyset (`WHERE sku > :cursor`) всегда читает ровно `limit` строк - 0.18 мс на
любой странице.

**`JOIN LATERAL (... LIMIT 1)` вместо обычного join.** Без `LIMIT 1` PostgreSQL
разворачивает подзапрос и на недооценке селективности уходит в merge join,
который прочитывает всю таблицу остатков: 2 мс, и растёт вместе с каталогом.
`LIMIT 1` мешает разворачиванию и фиксирует план: индексный проход по товарам,
затем ровно `limit` точечных обращений по PK. Стоимость перестаёт зависеть от
размера каталога.

**`VACUUM (ANALYZE)` после массовой загрузки.** Пока visibility map не обновлена,
`Index Only Scan` всё равно ходит в кучу, и от покрывающего индекса нет никакого
толку. Это делают и `scripts/load_catalog.py`, и `scripts/seed.py`. Тоже из
разряда «полдня искал, одна строчка».

**`ORDER BY type, sku` при фильтре по типу.** При фиксированном `type` это то же
самое, что `ORDER BY sku`, но совпадает с порядком ключа составного индекса, и
планировщик уверенно берёт покрывающий индекс вместо PK.

**Лишних индексов нет.** Отдельный индекс по `available` напрашивается, но его
здесь нет: витрина ходит в остатки только точечно по `sku`, а каждый лишний
индекс - это лишняя запись на каждой выдаче.

## Куда расти дальше

**Чтение.** Витрина уже не зависит от размера каталога. Дальше - реплики на
чтение и кеш страниц (ключ это фильтр плюс курсор, TTL десятки секунд, сброс
по событию изменения остатка).

**Запись.** Узкое место не выдача, а `sku_stock` при массовых продажах одного
SKU: все транзакции дерутся за одну строку. Лечится батчингом апдейтов или
«монетницей» - несколько строк-счётчиков на SKU с суммированием при чтении.

**Очередь.** `SKIP LOCKED` масштабируется добавлением воркеров линейно. Когда
таблица `jobs` станет горячей - партиционирование по `kind` и вынос завершённых
задач в архив. Отдельный брокер понадобится не раньше, чем у этих событий
появится второй потребитель.

**Заказы и события.** `orders` и `payment_events` растут монотонно, значит
партиционирование по месяцам и старые партиции в холодное хранилище. Шардирование
по `order_id` возможно без переделки логики: все критичные транзакции локальны
для одного заказа, распределённых блокировок нет.

**Поставщики.** Пул расширяется списком в `SUPPLIER_ORDER`, логика трёх исходов
от их количества не зависит. Чего сейчас не хватает - circuit breaker на
поставщика (ретраи с бэкоффом есть, размыкателя нет) и общего бюджета повторов
на заказ, чтобы один мёртвый поставщик не съедал воркеры.

## Время и рамки

Первый этап - примерно **4 часа** от разбора задания до репозитория с тестами
и документацией. Больше всего съели два места: разложить исходы запроса к
поставщику на три категории вместо двух и довести план витрины до
`Index Only Scan`.

Второй этап - ** примерно 4 часа**. Дороже всего
обошлись две вещи: денежная модель (пока обязательство перед клиентом не
гасилось выдачей, инвариант «оплачено = выдано + возвращено» нечем было
проверить) и лимит поставщика (скользящее окно на его стороне не дружит с полным
bucket на нашей, пришлось сузить bucket до строгого расписания и добавить запас).

Чего сознательно не делал:

- подпись вебхука не проверяется - в задании это явно исключено;
- схема создаётся идемпотентным DDL с миграционным блоком, а не Alembic;
- на `/admin/*` нет авторизации - в проде они за отдельным контуром;
- реального эквайринга, реальных поставщиков и фронтенда нет, как указано в
  задании;
- возврат денег доводится до проводки в журнале, но не до вызова платёжной
  системы: её тут нет.
